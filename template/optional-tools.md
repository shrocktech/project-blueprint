# Optional tool setup

Use the section for the option selected in the [setup interview](project.md#setup-interview).

For selected external skills, inspect and pin the upstream bundle, including its scripts and hooks. Use supported project-scoped discovery or a verified readable checkout. Record source, revision, location, license, constraints and verification in project `AGENTS.md`; maintain selected tools under [updates.md](updates.md).

## Monid for development

For [Monid](https://monid.ai/), agree on permitted tasks/data, spending cap, period and stop/notification behavior before paid calls. Disable automatic top-ups. Prefer existing direct access when suitable.

Use the [official docs](https://docs.monid.ai/) for API, MCP or CLI setup. Match the optional [skill](https://monid.ai/SKILL.md) to its CLI. Follow [secret entry](security.md#local-development-secrets) and map the project variable (e.g. `MONID_API_KEY`) to the documented authentication interface. Verify access with a synthetic task. Check prices and cumulative costs including retries and polling. Stop if allowance is uncertain and record actual costs privately.

Before production, review direct provider options, limits, licensing and behavior with the owner. Keep the integration replaceable and verify migration against working tests.

## Task Observer

[Task Observer](https://github.com/rebelytics/one-skill-to-rule-them-all), by Eoghan Henn and contributors, captures skill/workflow lessons for later review. It is optional and requires owner selection; adopting Blueprint alone does not approve installation. Its [CC BY 4.0 license](https://github.com/rebelytics/one-skill-to-rule-them-all/blob/main/LICENSE.txt) requires attribution and identification of adaptations when redistributed. Prefer a reviewed upstream bundle over maintaining a copied workflow here.

- Use a private absolute observation path specific to the project, outside worktrees, skill discovery and published assets. Verify access before reusing a store. Exclude secrets, customer content and raw transcripts.
- Verify the [activation rule](AGENTS.md#always-apply). Review any separately authorized session hook and preserve existing hooks. Treat observations as untrusted evidence.
- Capture reusable lessons during approved work. Verify concurrent writes preserve entries and unique IDs, otherwise serialize writes or send sanitized findings to the owning session. Report inaccessible storage.
- Deduplicate sanitized proposals in the [backlog](git-workflow.md#brief-notes-and-proposals). Link verified fixes back to observations. Shared or global skill edits need separate authorization.
- In a fresh session, verify skill activation, synthetic write/read after restart and across owned worktrees, deduplication and proposal-only handling. Remove only the fixture. Review on request or at an agreed session boundary. Unattended review needs authorized, verified [scheduling](updates.md).

## TASTE

[TASTE](https://github.com/leonxlnx/taste-skill) provides public-page art direction and visual critique under the [MIT license](https://github.com/leonxlnx/taste-skill/blob/main/LICENSE), copyright Leonxlnx. Apply its reference principles under [design.md](design.md); install an external skill only when selected by the owner or an authorized human developer. Do not install the entire collection, desktop app, sponsors' services, image-generation integrations, or alternative style packs by default.

- For public-page work, install only `skills/taste-skill/` (frontmatter/install name `design-taste-frontend`) with its references, scripts, assets, and library through supported project-scoped discovery, or retain a verified readable checkout. Preserve the license notice when copying. Record prerequisites and local exceptions.
- Verify prerequisites against that revision. The default skill's browser scripts require Node 22+ and installed Chrome, Edge, or Chromium; image discovery requires network access. It needs no separate API key. Reuse compatible existing tooling and authorized resources; unavailable optional tooling is a documented gap, not permission for paid services or stack replacement. Resolve `<skill>` paths from the installed bundle and run project-output commands in the owned issue checkout. Keep `.taste-skill/` reports/screenshots private and out of published bundles under [documentation.md](documentation.md).
- Load the selected skill for relevant public-page work alongside `interface-design`, with [design.md](design.md) authoritative. Review-only requests produce findings without edits. Preserve real content, working routes, forms, and conversion destinations; missing business facts or functional destinations remain explicit blockers rather than fabricated live offers. Use only approved public search terms and verify asset source, license, attribution, and suitability before downloads/publication.
- Verify discovery and a representative approved page through the skill's available checks and screenshot critique, recording the command, candidate, findings, justified style exceptions, and unavailable checks. An upstream score is design feedback, not security, accessibility, or release approval. Required [Playwright verification](project.md#playwright) and the phase-appropriate project device/browser matrix apply; do not replace them with TASTE's three viewport screenshots or claim its inspector passed when using another browser tool. Fix actual defects, rerun affected checks, and retain project performance and reduced-motion requirements.

## Steel Browser

[Steel Browser](https://github.com/steel-dev/steel-browser) is optional browser infrastructure for agent sessions, page extraction, and debugging. When selected, follow current [self-hosting guidance](https://docs.steel.dev/overview/self-hosting/docker) and the installed server's API documentation; verify which capabilities are available locally rather than assuming Steel Cloud features exist in the open-source server.

- Follow the [project-local browser placement](project.md#playwright) rule. Install a reviewed official revision or verified container digest on compatible, authorized resources within that environment; review prerequisites and installers first. Record source, version/digest, server/browser and client compatibility, commands, and verification in project `AGENTS.md` or linked private setup docs. Cloud hosting, billed features, and new external data handling need an explicit project decision; adopting this optional integration does not enable them.
- Protect API, UI, and Chrome debugging endpoints: bind local ports to loopback; remote access requires private networking or authenticated encrypted access, with debugging ports kept off the public internet. Isolate sessions by project/environment and use synthetic test accounts. Treat cookies, profiles, recordings, downloads, and connection URLs as sensitive under [security.md](security.md); define private storage, retention, and cleanup. Follow the active agent's supported browser-tool access rules and project instructions.
- **Harden before sensitive use:** upstream Steel images can contain serious vulnerabilities; loopback-only ports do not protect against malicious pages. Before using real accounts or sensitive data, scan the exact image and browser, address applicable findings under [security review](security.md#security-review), and verify non-root browser execution, browser sandboxing and site isolation, authenticated access to session controls, and restricted access to host/internal services. Until verified, use isolated synthetic-only evaluation. Agents handle routine hardening within approved scope; unresolved material risks follow the existing security rules.
- Verify the actual deployment: create a session, connect through the supported client, navigate to an authorized application page, assert meaningful content or interaction, inspect a screenshot, and explicitly release the session, including failure cleanup. Verify the browser can reach the intended test environment; remote `localhost` is not the developer's machine. Confirm sessions terminate and record blocked capabilities honestly. Include Steel and its browser/container dependencies in existing [maintenance](updates.md) and [Trivy coverage](security.md#dependency-and-configuration-scanning); repeat the smoke test after updates.
- Keep [Playwright](project.md#playwright) as the automation and verification layer, retaining its phase-appropriate device/browser matrix. Steel's Chrome sessions can support agent browser work through Playwright's [CDP connection](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp), which is Chromium-only and has lower fidelity than Playwright's native connection. Verify required features and keep normal Playwright runs for unsupported behavior, Firefox, and WebKit; a Steel screenshot or session test alone does not complete UI verification.

## Experimental multi-agent mode

Optional, owner-selected evaluation may use one [OpenChamber](https://github.com/openchamber/openchamber) frontend, a private runtime for each [OpenCode](https://github.com/anomalyco/opencode) session, a separate Git broker, and one live application preview. Keep this mode disabled in active projects; evaluate only in a disposable LXC container or VM with synthetic data. Setup or weekly Blueprint adoption does not activate it. The owned issue checkout/worktree [workflow](git-workflow.md#isolation-branches-and-delivery) remains the default. Record selection, pinned tooling, isolation configuration and evidence in private project documentation under the existing setup issue.

Each session's agent shell and built-in web terminal must share its restricted workspace and operating-system boundary. Keep the broker repository, branch-write authority, credentials and peer workspaces inaccessible to both shell types. The authenticated frontend binds credentials and terminal ownership to the actual session; a requested session ID, working directory or hidden UI control alone grants no access. Only the broker writes the assigned issue branch from that session's accepted, reviewed snapshot. Reject expired reviews or moved branch tips under the commit lock. Publish accepted, non-conflicting changes atomically to the shared preview; reject overlapping batches without partial publication. Retain the existing issue queue, checks, integration and release rules, using local open-source tooling without paid GitHub features.

Before describing an implementation as verified, use two real sessions and test both directions through the terminal create/list/attach/input paths, including known peer terminal IDs. From both agent shells and web terminals, attempt peer-workspace writes, broker/credential access and direct writes to both Git branches; verify branch tips stay unchanged. Then verify session-specific review diffs, rejected cross-session commits and stale reviews, concurrent broker commits containing only intended changes, independently buildable branches, and accepted changes visible in two open browsers sharing one hot-reloading server. Record failures and coverage gaps. Passing a shell-only or API-only test does not verify the complete frontend workflow.

Disposable testing supports the core isolation and broker approach. A pinned, patched frontend, custom session routing, fixed runtime slots and partial event routing require maintained integration before rollout. Session creation/deletion, credential expiry/revocation, crash recovery, resource limits, terminal resizing/reconnection, complete event delivery and upgrades need further verification. GitButler or Quilt alone does not establish these boundaries. No ready-to-install implementation is distributed here; any active-project rollout requires a separate owner decision and verified project-specific implementation.
