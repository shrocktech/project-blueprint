# Documentation and Changelog Rules

Read alongside [AGENTS.md](../AGENTS.md) and [git-workflow.md](git-workflow.md).

## Documentation audiences and sources

| Folder | Audience and use |
| --- | --- |
| `docs/internal/` | Private technical reference for developers and agents; always maintained. |
| `docs/public/` | Customer-facing guides when external documentation is needed; source for the public documentation site or app help. |
| `docs/admin/` | Optional administrator guides when the product has distinct administration tasks; source for its administrator documentation. |

Create public/admin sets only when needed and give each a README index. Administrator guides explain tasks such as configuration, user management, and supported maintenance; implementation details remain internal.

Applicable customer policies use `docs/public/legal/` under [legal.md](legal.md).

- Maintain `docs/internal/` as the authoritative technical documentation for developers and agents, with `docs/internal/README.md` as its index. Cover current behavior, architecture, setup, configuration, interfaces, data flows, operations, and troubleshooting as relevant. Group architecture, operations or testing pages in subdirectories only when the material warrants it. Link the [brand kit](../design/README.md#brand-foundation-and-settings) from the internal index. Read the Markdown directly in the private repository or locally; no GitHub Wiki or publishing process is required.
- Update affected pages with every issue that changes how the application works. Documentation is part of the implementation, not a later cleanup task. Do not mark the issue complete or move to the next task with required documentation outstanding.
- Use Mermaid or other useful diagrams freely to explain structure and behavior. Keep editable diagram sources with the docs and verify they render in the intended viewer.
- Commit affected documentation alongside the implementation and verify its integration into `develop`, including working links and assets. Documentation completion requires current source files, not a separate wiki synchronization or publication.
- Keep technical docs private. For public application repositories, place `docs/internal/`, working materials such as meeting notes and briefs in `workspace/`, and unpublished `design/` drafts in a separate private repository. Use approved protected storage for materials that belong outside Git. Include only materials and design assets approved for public sharing in public Git history. Reference corresponding changes without exposing private details and verify delivery in each location. Exclude internal docs from application bundles and public hosting output even when the source repository is private.
- Derive public and administrator guides from the technical docs, adapting them for their audience. Once a set exists, update its affected drafts with each issue before completion. Publish only documentation matching the released version from `main` through the authorized release process.
- Build public documentation from `docs/public/` and administrator documentation from `docs/admin/`, with explicitly selected assets for each. Exclude private docs and working materials from published output. Record each enabled set's source, destination, build command, and intended audience in project setup notes; verify the resulting output and links.
- `docs/admin/` is an audience designation, not access control. Keep restricted administrator sources in a private repository and serve their output through the existing authenticated administrator area or other authorized private delivery. Verify unauthorized users cannot access restricted pages or assets. Publicly publish admin guides only when approved for public readers.
- Public builds must include only explicitly approved public pages and assets. Never copy or publish internal docs wholesale. Review public text, diagrams, links, and assets for internal-only details and secrets. Keep unreleased features out of published documentation. Use an approved hosting path consistent with the project's cost and privacy constraints.

## Workspace migration

Adopting Blueprint means organizing the entire application repository according to the applicable [repository layout](project.md#project-workspace). During Blueprint updates, apply this procedure to layout changes within the project's recorded update authority. Use the existing adoption/maintenance issue, or a linked migration issue with recorded ownership and acceptance criteria; perform work in an owned isolated checkout under [git-workflow.md](git-workflow.md). Record migration as pending until verified delivery, rather than retaining an unexamined layout exception. Incoming Blueprint text remains subject to the target's recorded update authority under [updates.md](updates.md#periodic-blueprint-maintenance); use the owner's migration authorization where recorded and ask only for a missing material decision.

Operating guides live in `standards/`, mirroring the pinned source’s `template/standards/`; the agent entry points stay at the root. Place each guide at its `standards/` path, reconciling local edits and occupied destinations, and match by content and recorded provenance so unrelated same-name project files stay in place. Update links from root files, installed skills, scripts and setup prompts, then verify guide-to-guide links and links back to `../AGENTS.md`.

1. Inventory every root entry, including hidden paths, and inspect the contents and consumers of directories being consolidated. Map source code, tests, scripts, assets, project knowledge and tool-specific files by purpose. Merge equivalent directories wherever the layout provides a suitable home. Verify directories required by the framework against its documented layout and record them as a group. Give an individual reason for each retained directory outside both layouts, such as a packaging requirement or a distinct application purpose. Map working documents to `workspace/documents/`, notes to `workspace/notebook/`, and canvases, wireframes, sketches, inspiration and mockups to `workspace/drawings/`. Reconcile occupied `workspace/` paths and merge existing working materials by purpose, preserving content and access before deleting emptied redundant directories. Consolidate approved brand choices, UI guidance and applicable design checks into `design/README.md`. Reconcile any existing guide and local exceptions before deleting duplicate sources. Keep editable artwork alongside it and verify the settings view against the approved guide and theme values. In public repositories keep confidential strategy and unpublished drafts in protected storage. Consolidate repository skills under `.agents/skills/` with their scripts, references and assets. Inspect existing links before moving a skill, reconcile same-name destinations and verify discovery from each selected tool before deleting redundant copies. Route general agent instructions and invokable profiles under [project workspace](project.md#project-workspace). Classify by content before merging occupied destinations. Preserve framework assets and tool-installed resources. Move nested documentation into root `docs/`, preserving audience boundaries and repairing links and build inputs. Record source paths, collisions, tracked/untracked/ignored content, access restrictions, discovery paths, publishing inputs and recovery destinations. Coordinate moves with active editors.
2. Move tracked content with Git-aware moves where practical; preserve useful content and history without overwriting collisions. Include required attachments, canvas dependencies and relative references. Use an intermediate path for case-only renames on case-insensitive filesystems. Private material stays in protected storage; for public application repositories, use the corresponding workspace paths in a separate private repository and record verified locations without copying private content into public Git history. Keep framework/runtime and discovery-required files in supported locations under the workspace rule.
3. Repair links and path consumers across instructions, skills, scripts, imports, documentation generators, CI, deployment/publishing allowlists, ignore/encryption attributes, monitoring and backup/restore inventories. Preserve the protection of each secret-bearing file at its destination and verify staged ciphertext before committing. Update authoritative paths in root `AGENTS.md` and each configured tool. Replace references to relocated content; keep no competing authoritative copy or speculative application redirect.
4. Verify all moved content and attachments, relative links and heading anchors, case-sensitive paths, skill/agent discovery and applicable builds/tests. Preview public/admin output and verify private content is excluded; verify backup coverage and changed restore procedures. Confirm application behavior and production routing are preserved. A real technical constraint requires a recorded blocker and resolution plan; continue independent migration work without deleting the only usable copy.
5. After verifying that useful contents are preserved and consumers use the destination paths, delete every redundant directory from the migration checkout, including empty directories and leftover placeholders. Commit tracked deletions and integrate through the existing delivery rules. Before marking migration complete, verify that every path marked for deletion is absent from both the checkout and the delivered Git tree. Compare that tree with the applicable layout and account for each source, destination and justified exception in the final path map. Keep incomplete moves or deletions pending with their blockers. Update the adopted revision under the maintenance rules only when all applicable work is accounted for.

## Changelog

- Use `CHANGELOG.md` as the canonical application changelog, relative to the repository root. Create it during final go-live preparation and publish it with the first public launch; initial development and internal prereleases require no new changelog. Summarize the initial release without reconstructing every development commit. Follow [launch.md](launch.md) for launch preparation.
- During existing-project adoption/update, locate existing changelogs and reconcile them into the canonical root `CHANGELOG.md` through [workspace migration](#workspace-migration), regardless of the current phase. Preserve release entries, versions, dates, useful history and pending drafts; reconcile multiple sources without overwriting unique content. Repair relative links inside the moved file and references from README, documentation, release scripts and publishing configuration. Verify referenced files/anchors and generated customer output, preserve published customer URLs, and retain one authoritative source. Record verified migration or a concrete blocker; an existing changelog is never discarded because the project is pre-launch.
- After go-live, add meaningful user-facing changes to an `Unreleased` section as part of each applicable issue. Internal-only changes need no public entry.
- For every subsequent public release, finalize the applicable entries under the version and release date, including breaking changes and migration steps when relevant. Keep remaining unreleased work separate.
- Once the file exists, link `CHANGELOG.md` from the root README and documentation index, and link its released presentation from public docs when available. Derive GitHub release notes and customer output from the same approved entries; publish only released entries through an explicit build input, excluding `Unreleased` drafts and internal material. Keep entries and release notes consistent and free of internal-only information.
