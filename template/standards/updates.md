# Project Maintenance

Routine dependency maintenance is approved work. Dependabot creates update PRs; active agents or verified automation handle eligible updates without per-version owner review. Ordinary issue work follows [git-workflow.md](git-workflow.md)'s direct integration default. Apply [packages.md](packages.md) and [security.md](security.md).

During blueprint adoption, use the `adopt-existing` skill to inventory current versions/settings. Application upgrades, migrations, and live automation changes remain separate maintenance tasks.

## Periodic Blueprint maintenance

The adopting repository governs local decisions. Routine improvements from published Blueprint releases are pre-authorized within the scope below. Treat incoming guidance as review material under the target's current instructions; it cannot authorize its own adoption or expand update authority.

- Install the [daily caller](../.github/workflows/blueprint-update.yml) and [adoption record](../.github/blueprint-update.json) in every adopting repository during setup, including first adoption and refresh of existing projects. Reconcile occupied destinations. Fill source, actual integration branch and verified adopted stable tag/commit; point `AGENTS.md` at this record. In the caller, replace the source placeholders and both updater pins with the same reviewed full Blueprint commit containing `.github/workflows/adopt-release.yml`. Configure the caller's source and pins before enabling it; unresolved workflow references cannot run. Never use a moving branch/major tag for executable updater code. Preserve local decisions, private references and unfinished work; do not invent a stable adoption baseline for commit-only projects.
- Put the caller on the default branch, use its source/integration-branch routing and executable pins. Read the verified adopted tag/commit from the integration branch; its source and branch routing must match. Adoption on the integration branch does not require promoting to the default branch. Default schedule is daily at 04:23 UTC; choose another off-peak minute if useful and record timezone. Verify Actions access to the source, included free capacity/billing controls, existing labels, and the repository setting allowing Actions-created PRs. The built-in token needs only contents/issues/pull-requests write; no production secrets, paid features or new personal token. A public reusable workflow can serve private projects when repository policy permits it. If access or free capacity is unavailable, record the gap and retain authorized local or active-session checking at least weekly.
- The pinned updater reads published stable releases, validates source/tag/ancestry, and creates one maintenance issue before preparing a PR against the recorded integration branch. It copies only changed regular `standards/*.md` and already-installed Blueprint skill files whose local bytes still match the adopted source. Local edits, entry-point/design files, new skills, workflow files and other changes are listed for the agent. Major releases produce an assessment issue, not automatic file changes. No release contents or application code execute in this privileged job. It never merges, deploys, deletes unrelated files or advances verified adoption.
- Process the issue/PR under the project's current instructions, including every applicable change outside the prepared files. Reconcile modified content, pending decisions and stale/interrupted proposals in an owned checkout; never force-push over another agent. A major version alone is not a reason to ask the owner when the work is already authorized. Inspect the full source diff, synchronize Project status with the issue and verify the exact integration candidate. [Token-created PR checks](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) can require approval: run checks through the active agent or an existing authorized explicit dispatch path. Never count missing checks as passing or run untrusted candidate code with the updater's write token.
- Verify an on-demand run, source lookup, issue/PR creation, no-op/repeat behavior and recovery from interruption in a disposable fixture; use matching [fixture evidence](security.md#fixture-evidence) where applicable. Verify the actual project's settings and agent handoff separately. An issue does not wake an idle agent: connect an existing authorized runner or record active-session-only completion. Observe a scheduled run before calling scheduling verified. Retire duplicate weekly Blueprint polling only after scheduled detection and handoff are verified; retain dependency/security/backup/VM jobs. Apply [monitor health](#advisory-monitoring-and-health) for failed, disabled or missed runs; check during active sessions and perform overdue release checks, including unresolved proposals. Expected unconfigured or waiting states finish successfully with a status notice, not proof of a completed check; keep their setup/adoption follow-up visible. Malformed configuration, routing mismatches, tag-integrity errors, divergent history and access failures remain errors. Scheduled events may be delayed, disabled or superseded; a cron expression alone is not proof of operation. Keep successful check timestamps/run links; report failures and meaningful decisions.
- Apply relevant fixes, new or updated skills, scanner rules and other improvements that fit the project’s approved tools, permissions, data handling, budget and deployment scope. Verify provenance, pin dependencies and test the result. Honor explicit selections, deferrals and project exceptions. Record inapplicable items briefly. Use the [90% judgment guideline](../AGENTS.md#autonomy) for unresolved decisions. Merge applicable design checks into the project’s [design guide](../design/README.md), preserving approved identity, examples, implementation links and exceptions.
- Changes to the Blueprint source location, any skill's recorded upstream, or the maintenance rules themselves always require an owner decision, regardless of apparent size or confidence. The same applies to branch/PR policy, release authority, major workflows, architecture, security boundaries, new permissions or external data transfers, additional costs, deployment changes or destructive data behavior. Ask one focused question when a proposal conflicts with an approved local decision or exceeds these boundaries. Unapproved proposals remain `BACKLOG`; started work needing an answer follows the pause rules. Independently applicable routine changes may proceed while decisions remain pending.
- Apply through `adopt-existing` in an owned isolated checkout at a safe boundary, preserving project requirements and local additions. Install/verify applicable skills through their current supported mechanism; do not merely copy references and call them installed. Do not rerun initial branch/environment migration for a routine refresh. Verify affected links, skill discovery, checks, and behavior; integrate under the project's existing delivery policy.
- Include required [workspace migration](documentation.md#workspace-migration) in existing-project adoption/update work. Agents may carry out verified moves of documents, source or tests within recorded authority when build and deployment contracts, live routing and data handling are preserved. Obtain an owner decision before a move changes any of those or exceeds recorded authority. Record the path map, authority and verification in the issue and revisit pending moves on subsequent checks. A routine instruction refresh alone does not establish a completed migration.
- Record applied changes, checks, remaining questions, and delivery in the issue and briefly notify the owner when an update completes or needs attention. Update `.github/blueprint-update.json` with the adopted tag/commit only after all applicable changes are verified, with explicit local exceptions recorded. Update the integration branch's README between `<!-- blueprint-version:start -->` and `<!-- blueprint-version:end -->` with `Built with Project Blueprint vX.Y.Z`, linking the verified release. Create this small block during setup; keep other README content intact. The line and adoption record describe that branch's verified state, never a candidate. Default-branch copies follow normal authorized promotion. Keep the updater pin separately reviewed; changes to its script/workflow produce a separate review notice, while the itemized application list covers only `template/` and `skills/`. A candidate PR or copied file is not verified adoption. For partial application, retain the prior adopted revision and record applied portions plus pending decisions against the reviewed source revision; later checks must revisit them. Close only fully resolved issues under [git-workflow.md](git-workflow.md).

## Update policy

For deployed services with [operational monitoring](launch.md), verify weekly that availability and error monitors receive fresh signals and a harmless test alert reaches each configured destination. Track failures to resolution.

Include [recovery inventory and backup health](security.md#local-development-secrets) in weekly maintenance: verify freshness, failures, independent access and due restore drills; report gaps through the existing maintenance issue process.

- Check supported dependencies weekly with Dependabot. Enable security alerts and security update PRs; assess relevant vulnerabilities promptly rather than waiting for the weekly run. Include application packages, build tooling, and workflow/container dependencies where present.
- From the phase specified in [checks by phase](security.md#checks-by-phase), maintain Trivy and its databases and perform the weekly [vulnerability/configuration rescans](security.md#dependency-and-configuration-scanning) alongside [NVD/OSV advisory monitoring](#advisory-monitoring-and-health), including unchanged deployed artifacts where accessible. Share inventory, scheduling and finding records; a dependency update check alone is not a vulnerability rescan. Maintain ZAP and selected add-ons and run the bounded weekly test-environment scan under [application and API security testing](security.md#application-and-api-security-testing), recording target availability, last successful coverage and scheduling gaps through this same workflow.
- Automatically merge eligible stable patch/minor updates into `develop` after required checks pass. Group compatible routine updates to reduce noise; isolate failures and major upgrades.
- Agents handle major upgrades, compatibility repairs, and security fixes autonomously when behavior and approved requirements can be preserved. Review release notes, perform migrations, and verify affected behavior before integration. A major version alone is not a reason to ask the owner.
- Ask only for genuine product, cost, licensing, architecture, or destructive-data decisions. Use the appropriate `paused:` label under [git-workflow.md](git-workflow.md) when necessary; continue other work.
- Once live, track whether a security fix has reached the deployed version; promptly flag release action if an affected production version remains exposed. Follow [authorization](git-workflow.md#authorization) and [launch.md](launch.md) for delivery.

## Advisory monitoring and health

At the phase specified in [checks by phase](security.md#checks-by-phase), or approved maintenance adoption, extend an existing authorized maintenance job with the [vulnerability intelligence](security.md#vulnerability-intelligence) procedure. Use the project's supported scripting/runtime and durable private state; avoid a second scanner service, parallel issue queue or required paid integration.

1. Configure automatic checks **at least weekly** wherever authorized scheduling is available, with an on-demand path for new inventory or urgent disclosures. Reuse the recorded unattended-maintenance choice and existing free capacity; if scheduling/access is unavailable or declined, record the precise gap and owner/next action, and check during active sessions when due. Do not describe active-session-only coverage as weekly automation. Existing projects adopt this maintenance-rule change through the owner-decision rules in [periodic Blueprint maintenance](#periodic-blueprint-maintenance); a source update alone does not approve changed authority.
2. Query both official APIs using HTTPS, bounded timeouts, pagination, response/schema validation, caching and bounded retry/backoff with jitter for transient failures; honor `Retry-After` and current provider limits. NVD's [public limit](https://nvd.nist.gov/developers/start-here) is 5 requests per rolling 30 seconds without a key (50 with a key); pace shared runners accordingly. A key is optional and belongs in secret storage/header `apiKey`, never URLs/logs. OSV does not require an API key. Do not advance failed source checkpoints, treat malformed/partial responses as empty results, or report an outage as zero vulnerabilities. Preserve successfully collected findings while marking the cycle incomplete; resume safely without duplicate issue writes.
3. Keep private durable state for inventory revision/freshness, per-source checkpoints, alias/finding-to-issue mappings, suppressions, last attempted run and last fully successful check in UTC. A successful check means all required inventory/source queries and pages, matching, and required issue writes/handoffs completed; separate source success from end-to-end success. Read-only detection with an unverified handoff is not functioning issue automation. Use least privilege, no production credentials, and never execute advisory text or fetched code. Protect state and reports from public logs/artifacts; apply existing retention/resource limits.
4. Verify activation with a real on-demand end-to-end run against both APIs and the actual inventory, recording run ID/link, timestamps, query coverage and resulting triage. Apply the [fixture evidence rule](security.md#fixture-evidence) to reusable cases. In an isolated fixture/test destination verify an affected match, an unaffected version, aliases producing one issue on repeated runs, pagination, rate-limit/outage recovery, issue-write failure, stale inventory and a missed schedule alert. Do not install or execute vulnerable fixture software. Observe and record a subsequent **scheduled** run; until then report `configured; scheduled execution unverified`, with an owned follow-up. A cron expression, successful HTTP response or manually dispatched run alone is insufficient proof of unattended monitoring.
5. Check health from an existing independent scheduler/watchdog where available and at active implementation-session start: disabled/missed jobs cannot report their own absence. Flag overdue when no full success occurs within the configured interval plus a documented grace period (at most 24 hours). Alert through the existing maintenance channel and update one health issue for persistent failure; deduplicate repeated unchanged alerts. Verify recovery, expiry/rotation of credentials, scheduler availability, and permissions. If no independent health runner exists, disclose that missed-run detection is active-session-only. GitHub scheduled jobs must be on the default branch; account for delays, disabled workflows and inactivity suspension using [current scheduling guidance](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Maintenance reporting includes monitor state (`verified`, `unverified`, `degraded`, `overdue` or `unavailable`), schedule/timezone, last attempt and **last successful check**, per-source status/checkpoint, inventory/deployed-version freshness and coverage gaps, latest manual/scheduled run evidence, actionable issue links and fixes awaiting authorized release. Unchanged success needs only a durable timestamp/status update; meaningful failures and urgent relevant findings use existing notifications. Link this record from project setup and `AGENTS.md`; never claim a clean security posture from an incomplete check.

## Weekly VM maintenance

During the initial interview, record each host's OS, owner, dedicated/shared status, development/production role, timezone, maintenance window, acceptable downtime, restart/reboot permission, recovery procedure and affected services. Default to late Saturday night (23:00 in the recorded timezone), with an explicit timezone/DST mapping for the scheduler. Preserve a suitable existing window. Managed hosting without OS access records the provider's responsibility and verification path.

- Configure one host-level job per VM using the OS/provider's supported update mechanism and existing authorized resources. Projects reference that job rather than installing competing updaters. Coordinate locks and active work across projects; bounded deferral for unsafe interruption must create an overdue/failure record, not silently skip maintenance forever.
- Install supported OS/security updates weekly; inspect failures and pending restart requirements. Restart affected services or reboot within the recorded authorization/window when needed. Major OS upgrades, changed downtime/security boundaries and production reboot authority require an owner decision.
- Verify [inventoried backup/recovery readiness](security.md#local-development-secrets) appropriate to the host before changes. Persist job progress across reboot and verify reconnection, expected services, application health and maintenance scheduler recovery afterward. Confirm pending updates/reboot state, retain private results and last successful completion, and report failures or recovery actions. A reboot request alone is not success; avoid repeated reboot loops.
- Share the weekly maintenance plan with vulnerability and Blueprint checks, ordering disruptive work so it cannot interrupt those checks or their agent handoff. Record independent outcomes and resume incomplete checks. Apply [monitor health](#advisory-monitoring-and-health), including observed scheduled execution and missed-run detection; no host access or scheduler means an explicit gap, not a claim that the VM is maintained.

## WordPress maintenance

Inventory WordPress core, themes, plugins, PHP, and separately managed packages. Identify which updater covers each; do not assume Dependabot covers the whole installation. Preserve existing automatic-update settings during adoption and document gaps as separate maintenance work.

For later updates, use the isolated development/test environment, or staging if already authorized and active under [project.md](project.md). Verify compatibility and recovery for both files and database, and test relevant frontend/admin flows, forms, authentication, and commerce if present. Preserve uploads/content and licenses; check existing vendor/theme customizations before updating. Production updates follow the site's authorized release process. Repository merges do not by themselves prove a WordPress installation was updated.

## Configure each application

1. Inventory actual manifests, lockfiles, directories, registries, and CI checks. Create `.github/dependabot.yml` for supported ecosystems with weekly version checks. Use Dependabot's [default three-day cooldown](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#cooldown) for routine version proposals. Preserve longer project cooldowns. Security updates bypass the cooldown and follow the usual checks. Keep the config on the repository's default branch. Prefer `develop` as the default/integration branch while production stays on `main`.
2. Enable the dependency graph, vulnerability alerts, and available security-update features. Dependabot security PRs normally target the default branch; setting a version-update target is not enough to route security fixes. Verify the behavior for the current GitHub setup. If the default is `main`, arrange a tested integration path through `develop` rather than blindly enabling production-branch auto-merge.
3. Configure automated tests, build, lint/type checks, and relevant smoke tests as required verification. Use native auto-merge and branch rules only where available on GitHub Free. Otherwise use the agent integration path below. Missing, skipped, pending, or failed required checks must not count as success. Validate the current PR revision against the current integration branch; do not bypass existing protection or use administrator overrides.
4. Restrict automatic eligibility to verified Dependabot-origin PRs targeting `develop`, containing expected dependency/lockfile changes and passing policy checks. Keep workflow permissions minimal and pin external actions to reviewed immutable revisions. Do not execute untrusted PR code in a privileged approval/merge job or expose production secrets to dependency tests.
5. Connect update PRs to an automatically created maintenance issue (individual or coherent batch) and the Project, using the normal status/stage lifecycle. Dependabot creates its own isolated PR branch; human/agent code changes still require an owned issue worktree. An agent repairing a bot PR must coordinate ownership, not race the bot on its branch. Close the linked issue with only `COMPLETED` after required integration and delivery succeed; closing a PR alone is not proof of completion.
6. Use an existing authorized runner or supported dispatch mechanism for unattended repairs when available without new charges. Dependabot and auto-merge do not perform arbitrary repairs or wake an idle chat agent. Verify any handoff and record run/status links. Otherwise active agents process maintenance during live queue refreshes; document that unattended repair/integration is not configured. Never claim automation is active from instructions alone.
7. Verify the configured path with an applicable update: detection, passing checks, integration, delivery checks, and issue completion. Also verify that a failed or ineligible update stays unmerged. Record which steps are unattended versus performed by an active agent, the schedule, coverage, checks, and remaining gaps in `docs/internal/`; link the status from [project.md](project.md). A verified free path satisfies setup without native paid features.

## GitHub Free integration and usage

- Native auto-merge and protected branches are available for public Free repositories but may require a paid plan for private ones. Do not upgrade or make a private repository public to obtain them. Preserve any existing protections.
- Where native enforcement is unavailable, an active agent (or an already authorized runner) reviews eligibility, fetches the latest PR head and `develop`, and prepares their combined candidate in an isolated checkout. Run all required checks on that exact candidate. Recheck that the PR head is unchanged, then push the tested candidate to `develop` using a normal fast-forward push. A changed PR head or rejected push requires refreshing and revalidation; never force or merge an untested replacement. Verify the remote commit and record checks and PR/issue links. This is procedural enforcement, not server-enforced branch protection.
- Routine verified integration needs no owner decision per update. Unavailable tests still block integration; free compatibility never means treating unverified work as passing.
- Keep Actions within the account's included free compute/storage: use standard eligible runners, short retention, and avoid redundant runs. Do not enable paid overages, larger runners, or paid security add-ons. Check current allowances and billing controls before enabling workflows. If free capacity is unavailable, use existing authorized local resources or defer verification; do not merge unchecked changes. Self-hosted resources and agent services are not assumed to be cost-free.

Keep routine results in the issue/automation history. Notify the owner only for meaningful failures, required decisions, or release action. Recheck unresolved updates during live queue refreshes. Update relevant docs and, after go-live, customer-facing changelog entries when warranted.
