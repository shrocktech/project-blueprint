# Project Phases

Read the current phase, subphase, and active plan in [AGENTS.md](../AGENTS.md) when starting or resuming work. These describe project focus; issue statuses, work stages, branches, and deployment environments remain separate.

Seven stops in fixed order; the stop number is display-only and never typed in transitions.

| Phase | Subphases and focus | Ready to advance when |
| --- | --- | --- |
| `DEVELOPMENT` | **1** `planning`: agree specifications: audience, scope, workflows, acceptance criteria, APIs/vendors, data/security requirements, and issue plan; for projects with an interface, approve the [brand foundation](../design/README.md#brand-foundation-and-settings), [UI foundation and shared-control plan](../design/README.md#design-interview) before styled UI; finish by configuring and verifying services, tools, and the application skeleton. **2** `build`: begin UI work by building or extending the planned shared controls before feature screens; implement, test, and document under the light [checks by phase](security.md#checks-by-phase). **3** `security`: install and run the full check set, then review, fix, and retest under [security.md](security.md). | The first version passes internal acceptance checks and the full security review. |
| `LAUNCH` | **4** `prepare`: finalize what the project offers under [offering.md](offering.md) where it has a website, pricing or policies, complete customer documentation and readiness under [launch.md](launch.md), run a private beta only when the project wants one, resolve launch blockers, and recheck affected security controls and final data-handling claims on the candidate. Open only when critical journeys and security checks pass, any offer matches the product, and the owner authorizes opening. **5** `open`: open access and publish the release. **6** `stabilize`: assess actual use and resolve significant early problems. | An agreed period of real use meets reliability criteria; support, recovery, and releases work routinely. |
| `PRODUCTION` | **7** No subphases. Continue marketing, growth, support, maintenance, and approved feature releases. | Final ongoing phase; an empty backlog is not required. |

The user directs transitions. Accept natural wording: “planning” means `DEVELOPMENT: planning`; “move to security” selects `DEVELOPMENT: security`. Apply [authorization](git-workflow.md#authorization) to ambiguous transitions. Verify each subphase's work and applicable phase-exit criteria; recommend advancement with evidence and remaining decisions, then await approval without repeated nudges. Explicit transitions need no second confirmation. Continue independent approved work while awaiting a decision; do not silently skip unresolved requirements.

Record approved transitions in `AGENTS.md` and the relevant issue. Store the living specification in private `docs/internal/specification.md` or link an existing plan under [documentation.md](documentation.md). Phases guide priorities; authorized work may overlap. Future features do not reset the whole product from `PRODUCTION`.

Record and display parents uppercase, subphases lowercase, prefixed by the stop number out of seven: `2/7 · DEVELOPMENT: build`, `4/7 · LAUNCH: prepare`, then `7/7 · PRODUCTION`. Phases are not GitHub issue labels or Project fields; the admin footer shows the current stop under [project design guide](../design/README.md#environment-and-phase-display). Commercial work follows [offering.md](offering.md), including after launch.
