# Security Defaults

Apply alongside [AGENTS.md](AGENTS.md). Keep implementation details and reporting procedures in private `docs/internal/`, without secret values.

- **Secrets and logs:** Never commit plaintext credentials or expose them in logs, errors, screenshots, issue reports, URLs, or client bundles. Keep customer content and personal information out of diagnostic outputs. Examples use placeholders; review staged changes.
- **Test data:** Use synthetic data by default. Production data requires explicit authorization and documented safeguards. Separate development/test resources from production.
- **Access:** Use credentials proactively within approved scope and least privilege. Enforce authentication, ownership, tenant boundaries, and authorization server-side; test allowed and denied cases. Do not disable controls or request blanket administrator access to make a task pass.
- **Reporting:** Use the documented private vulnerability channel. If missing, ask privately; do not invent a contact or publish sensitive evidence. An exposed secret requires notification and authorized revocation/rotation; deleting its visible text is insufficient.

## Checks by phase

Light checks apply from setup; the full set switches on at `DEVELOPMENT: security` and stays on for every later phase. A project cannot leave `DEVELOPMENT` until required checks pass and findings meet the [security review](#security-review) acceptance rules under [phases.md](phases.md), so nothing reaches beta or `main` on light checks alone.

| Check | `planning` and `build` | From `security` onward |
| --- | --- | --- |
| [Secret scanning](#secret-scanning) (Betterleaks) and [encrypted `.env`](#encrypted-env-with-git-crypt) when selected | Required at setup, every commit and integration | Required at every commit and integration |
| Release rule: no `main` or production change without explicit release authorization | Always | Always |
| [Trivy](#dependency-and-configuration-scanning) | Not yet installed | Install, run before each integration, weekly thereafter |
| [Delegated code review](git-workflow.md#delegated-code-review) (Open Code Review) | Agent's own review of the candidate | Applicable integration changes and every production promotion; exclusions follow the linked workflow |
| [Playwright](project.md#playwright) for web UI | Installed at setup; desktop checks | Full desktop/tablet/mobile matrix |
| [Lint/format](packages.md#linting-and-formatting), existing tests and meaningful behavior checks | Required as applicable | Required as applicable |
| [Graphify](project.md#graphify) | Installed at setup; a failure is recorded, not blocking | Required working |
| [Vulnerability intelligence](#vulnerability-intelligence) (NVD/OSV monitoring) | Not yet configured | Configure and verify under [updates.md](updates.md) |

Entering `security` means installing and verifying every item in the right-hand column and running the first full pass; record results in the transition issue. Existing projects keep their current coverage; adopt this table through the recorded update policy.

## Local development secrets

Every adopting project has a `.env` at its project root for local development credentials. During setup create it if missing, preserve existing contents, and verify Git ignores it before writing secrets, unless the owner selected [git-crypt](#encrypted-env-with-git-crypt), in which case `.env` is tracked only in encrypted form. Keep a tracked `.env.example` with variable names and empty placeholders only. Ignore secret-bearing environment variants too while allowing the example; if a secret file is tracked in plaintext, remove it from tracking while preserving the local file, assess exposure and follow the reporting rule. Ignore rules do not remove history.

- When the owner offers an API key/password, immediately add the appropriate empty variable if absent (for example `MONID_API_KEY=`), and provide a clickable absolute path to that `.env` with instructions to paste the value locally. Use names the integration expects or document the mapping. Never overwrite a populated entry with a placeholder or duplicate its name; preserve unrelated entries. Never request secrets in chat.
- If a credential is accidentally supplied in chat, save it to that root `.env` using a non-echoing write without repeating it in messages, logs or command output. Resolve any ambiguous destination or conflicting existing credential without exposing either value. Explain that saving it does not erase the chat exposure and recommend replacement; revocation/rotation follows existing authorization. If the available tool would expose the value, prepare the placeholder and direct local entry instead of reproducing the secret.
- Identify the exact active project/worktree root and authoritative local credential file. Use the recorded ignored or encrypted mode in every worktree; verify its local file and unlock state without silently sharing production credentials. Restrict file access to the user/service that needs it, keep it outside served content, and exclude it from images, build artifacts, public docs and browser bundles. Verify denial of HTTP access where the root could be served. Never use public/client-prefixed variables for secrets.
- Use the stack's supported environment loader and correct quoting for special characters; creating `.env` alone does not load it. Do not source it as arbitrary shell code. Verify presence and authentication without dumping values, environment output or credential-bearing URLs/arguments. Review `.env.example` for accidental values before committing.
- Production credentials belong in the deployment platform's protected environment/secret settings, with local `.env` reserved for approved development/test values. Preserve existing secure production storage; a supplied key is not permission to distribute it, change production configuration or enable paid usage.

## Encrypted `.env` with git-crypt

Owner-selected alternative to an ignored `.env`: use [git-crypt](https://github.com/AGWA/git-crypt) to keep plaintext only in authorized unlocked checkouts and ciphertext in Git. Record the key path and authorized users/hosts in `AGENTS.md`; an owner-selected shared symmetric key grants access across every repository using it. Keep the recovery copy in the owner's password manager and restrict all machine and unlocked-checkout copies. Use an absolute protected path outside repositories; on Linux, `/etc/secrets/git-crypt.key` with `root:secrets` ownership and mode `640` is one option. Other platforms use equivalent restrictive permissions.

- **Session start, every checkout:** verify the installed tool, readable recorded key, encryption attributes/filter configuration and `.env` unlock state without displaying values. `git-crypt status` checks protected paths; it alone does not prove the working file is decrypted. Use the documented unlock command with the recorded key when needed, preserving uncommitted work. If the key is missing/unreadable or unlock fails, follow `paused: setup` in [git-workflow.md](git-workflow.md), provide machine-specific local setup instructions, and re-verify before secret-dependent work. Never request keys in chat, expose them in command arguments/logs, copy them into a repository or `.env`, or hand-edit git-crypt internal key files.
- **Repository setup:** follow [upstream symmetric-key setup](https://github.com/AGWA/git-crypt#using-git-crypt), using initialization for a new key or the documented unlock/import path for the recorded shared key. Set encryption attributes before staging any secret file: root `.env` and secret-bearing variants use `filter=git-crypt diff=git-crypt`; `.env.example` explicitly clears both attributes. Keep `.gitattributes` readable. Reconcile ignore rules only for verified encrypted paths, then verify attributes, clean-filter operation and raw staged ciphertext before each commit. Check committed ciphertext without text conversion or printing bytes; a magic header alone is insufficient. Prove a synthetic value round-trips through a fresh locked clone and authorized unlock before real credentials are added.
- **Machine setup:** tell the owner to run the machine setup command stored alongside the key in their password manager, pasting the key at its prompt; do not compose a substitute command. That stored command installs the supported tool and prompts silently for the key locally. Disable tracing, use restrictive temporary-file permissions, validate decoding and key import with a synthetic protected fixture, then atomically install the key with least-privilege access. Fail without replacing an existing working key; clean temporary material on failure and success. For group-based access, require a fresh login and verify the agent/service user's access before unlocking.
- **Scanning:** scan staged and committed ciphertext plus all unencrypted content; encryption is not a scanner pass. Keep redacted scans of first-party code and accidental plaintext copies. Document a narrowly scoped expected-secret exception only for the intentionally decrypted, protected environment paths in local scans; never blanket-exclude other findings. Plaintext committed to Git is exposure under the reporting rule regardless of encryption elsewhere.
- **Key generation and rotation:** generate/export keys only in an owner-run private local session using upstream-supported commands and transfer them directly to protected storage; agents must not display them. [git-crypt does not support key rotation or access revocation](https://github.com/AGWA/git-crypt#limitations). For compromise, rotate affected credentials and obtain an explicit migration/recovery plan; do not replace internal key files or claim repository history is revoked. Preserve needed recovery access under the owner's retention policy.
- **Deployment hosts:** use protected platform settings by default. A Git-deploy host may unlock only with explicit authorization for that host, service user and credential scope. Keys and decrypted files stay out of public output, CI artifacts and images; CI key access requires explicit authorization.

## Secret scanning

Secret scanning is required infrastructure. Use [Betterleaks](https://github.com/betterleaks/betterleaks) for new setups; preserve verified existing Gitleaks coverage during adoption rather than disabling it. Follow current upstream installation and [scanning guidance](https://github.com/betterleaks/betterleaks/blob/main/docs/scanning.md).

- Install a verified official release and record its version, configuration, and commands in project setup docs, with commands linked from `AGENTS.md`. Scan working files and repository history during setup; fetch the history needed for the recorded scope rather than treating a shallow checkout as complete coverage.
- Install and verify a staged-change pre-commit check without replacing Graphify or other hooks. Before integration, independently scan the exact candidate's files and incoming commit history; hooks alone do not establish a pass. Findings or scan errors block delivery until resolved or narrowly adjudicated below. Missing/skipped checks are not passes.
- Verify detection and a failing check with a harmless synthetic secret fixture in an isolated temporary test repository, then verify clean input passes. Never use real credentials or commit the fixture to the application repository.
- Enable redacted output and keep findings/reports private; never paste secret values into issues, logs, or shared artifacts. Investigate every finding. Allow only narrow, documented false-positive, confirmed revoked-secret or [intentionally decrypted environment-file](#encrypted-env-with-git-crypt) exceptions; never blanket-baseline unresolved credentials. Handle exposed secrets under the reporting rule above. History rewriting requires separate authorization.
- Keep live credential validation disabled by default; provider requests require authorization for that scope. Maintain the scanner and review rule changes under [updates.md](updates.md), retesting detection after changes. Use its CLI locally and in authorized CI within existing resource limits; neither paid services nor uploaded security reports are prerequisites. Record automation gaps and retain local checks when CI is unavailable.

## Dependency and configuration scanning

[Trivy](https://github.com/aquasecurity/trivy) is required security tooling for adopting projects from `DEVELOPMENT: security` onward under [checks by phase](#checks-by-phase). Use it for supported dependency vulnerabilities, infrastructure misconfigurations, and shipped container images; Betterleaks remains the required secret scanner. Follow current [installation](https://trivy.dev/docs/latest/getting-started/installation/) and [scan coverage](https://trivy.dev/docs/latest/coverage/) documentation.

- When entering `security`, inspect current [upstream security advisories](https://github.com/aquasecurity/trivy/security/advisories), install a verified official release using upstream [signature/checksum verification](https://trivy.dev/docs/latest/getting-started/signature-verification/), and record its version, source, configuration, commands, and coverage in private project docs. Pin CI actions to reviewed full commit hashes and scanner containers to verified digests; pin the CLI version separately when an action downloads it. Update deliberately under [updates.md](updates.md), rather than executing floating `latest` references.
- Inventory actual lockfiles, build dependencies, infrastructure files, and release artifacts. Explicitly enable applicable vulnerability and misconfiguration scanning (normally `--scanners vuln,misconfig`); review development-dependency coverage and exclusions. Scan the exact built image by digest when shipping containers. A source scan does not cover the deployed operating system or every build artifact. Record unsupported components and the complementary checks needed; zero detected packages is not proof of safety. For WordPress, [Composer coverage](https://trivy.dev/docs/latest/coverage/language/php/) does not establish coverage of all installed core, themes, and plugins: inventory them and verify applicable vendor/WordPress vulnerability checks separately.
- Run an initial baseline and applicable scans of each integration candidate, and applicable scans of the exact candidate before every production promotion. Rescan maintained projects weekly for newly disclosed vulnerabilities, including the recorded deployed version/artifact where accessible. Use current vulnerability databases and record scan time, database freshness, candidate/image identity, covered targets, and gaps. Unattended checks follow the recorded maintenance choice; without a verified runner, perform checks during active sessions and disclose the scheduling gap.
- Configure a nonzero result for blocking findings and verify both detection/failure and clean/pass behavior with harmless isolated fixtures, without executing vulnerable software. Scan errors, stale/unavailable required databases, skipped checks, or missing required coverage are incomplete verification. Retain a complete report for triage; do not hide unfixed vulnerabilities simply because no patch exists. Confirm findings, fix and rescan, and use the existing [security review](#security-review) severity and owner-only risk-acceptance rules. Keep exclusions narrow, evidenced, tracked, and time-bounded; preserve accepted findings in the record.
- Keep detailed results private. Run with minimal permissions and without production secrets, using authorized local or CI resources within existing limits. Paid dashboards, public report uploads, and paid GitHub security features are not prerequisites. Optional license scanning or software inventories support project needs; scanner license categories do not determine legal approval.

## Vulnerability intelligence

Extend the existing Trivy/Dependabot maintenance path with direct official [NIST NVD CVE API 2.0](https://nvd.nist.gov/developers/vulnerabilities) and [Google OSV API](https://google.github.io/osv.dev/api/) checks. These advisory sources complement scans and vendor notices; they neither replace scanners nor authorize fixes or releases. Configure execution and health under [updates.md](updates.md#advisory-monitoring-and-health).

- **Inventory first:** Reuse lockfiles, scanner/SBOM output, build manifests and read-only deployment records. Include direct/transitive and development/build dependencies, frameworks, runtimes, OS/distribution packages, container base images by digest, and installed plugins/themes. Record ecosystem/package identity (or purl), exact resolved version, environment, artifact/commit, inventory timestamp and evidence. Track deployed versions independently of repository versions. Unknown/stale deployment data, unsupported ecosystems and unmapped products are coverage gaps, never clean results. Do not access production beyond existing authorization.
- **OSV matching:** Send public package identity and exact version to `POST https://api.osv.dev/v1/querybatch` (or `/v1/query`); use ecosystem-specific names/versions, not dependency ranges. Follow each result's `next_page_token` using that query's `page_token` until exhausted, preserving input/result mapping. Batch responses contain IDs/modified times: retrieve full records with `GET https://api.osv.dev/v1/vulns/{id}` for aliases, affected ranges, fixes and references. Requery the full maintained inventory each cycle so newly published or revised advisories match unchanged installations. Do not send private package names, source, credentials or internal infrastructure identifiers to public APIs; record excluded coverage and use approved private/local checks.
- **NVD matching:** Use `GET https://services.nvd.nist.gov/rest/json/cves/2.0` with verified `cpeName` mappings for products/versions and `cveId` for known aliases. Resolve mappings using the official [CPE API](https://nvd.nist.gov/developers/products); keyword searches only produce candidates. Evaluate configuration AND/OR/negation, vulnerable flags, platform prerequisites and version bounds, then confirm against vendor/distribution advisories, including backported fixes. Never compare arbitrary versions lexically or equate a name match with exposure. Missing CPE/enrichment or disputed applicability requires triage, not dismissal. Baseline all mapped installed versions; repeat full matching when inventory changes. For incremental retrieval, use overlapping UTC `lastModStartDate`/`lastModEndDate` windows from the last completed checkpoint, split gaps into windows of at most 120 days, and exhaust `startIndex`/`resultsPerPage` through `totalResults`. Persist checkpoints only after complete processing; periodically repeat the full baseline to reconcile mapping/data changes.
- **Priority and evidence:** Triage confirmed active exploitation first (NVD CISA KEV fields/`hasKev`, verified against the [CISA catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) or original vendor notice), then applicable critical/high findings and other direct project impacts, considering exposure and prerequisites. Absence from KEV does not prove absence of exploitation. Preserve source CVSS score/vector/version and separately record project risk under [security review](#security-review); missing severity is unknown, not low. Do not filter retrieval to high scores or patched findings. Consult original disclosures for urgent or incomplete records rather than waiting for NVD enrichment. Mark `AI-assisted discovery: confirmed` only when the original disclosure explicitly confirms it, with its link and supporting quotation; otherwise use `not established`. Discovery method does not change applicability or severity.
- **One actionable record:** Normalize CVE/OSV/GHSA aliases and key by advisory alias group plus component identity, grouping affected versions/environments in one finding. Search open and closed GitHub issues, existing Trivy findings and Dependabot alerts/PRs before creating an issue; link and update the existing remediation record. Serialize writers or use a durable key-to-issue mapping and recheck before creation to prevent races. Create/update an actionable GitHub issue through the existing private reporting channel and [issue lifecycle](git-workflow.md), with CVE (or OSV/GHSA ID when none assigned), component, installed/affected versions and environments, severity, exploitation/applicability evidence, recommended fixed version or mitigation (or no fix available), source/disclosure links, first/last seen times, and linked update PRs. On public repositories, use the documented private issue destination; if unavailable, resolve reporting access privately before publishing details.
- **Noise and follow-through:** Unrelated advisories stay out of the board; uncertain matches go to a bounded triage/coverage record with owner and next review date. Update issues only for material changes, not unchanged weekly comments. Keep narrow suppressions with evidence, owner and expiry; reevaluate when inventory, advisory or exposure changes. Handle withdrawn/rejected advisories and merged aliases without leaving duplicate work. Reopen a resolved finding only on evidenced recurrence; never auto-reopen valid risk acceptance on every run. A merged patch does not resolve affected production: retain deployment follow-up until the deployed fix or mitigation is verified. Apply existing owner-only risk acceptance and release authorization; advisory automation must not deploy, mutate production, or close unresolved exposure as fixed.

## Credential storage

- Hash login passwords with the supported framework's salted adaptive password APIs; prefer Argon2id for new custom authentication where supported. Preserve WordPress's native APIs and upgrade path. Never store plaintext/reversible login passwords or use a fast general-purpose hash. Offer reset/change, not retrieval.
- Protect recoverable provider secrets with existing secret storage or a maintained authenticated-encryption library. Follow its key generation/nonce requirements; do not invent cryptography. Tokens needed only for local verification may use an appropriate non-recoverable verifier. Masking and encoding are not encryption.
- Keep encryption keys separate from credential records and database backups, outside source control, web roots, and bundles. Limit decryption to authorized server operations; fail closed on missing keys or failed authentication. Document key versions, rotation, protected backup/recovery, and any existing gaps. Do not casually rotate unrelated framework keys/salts.
- Use HTTPS. Normal settings responses expose only presence/status and permitted API-key previews to authorized credential managers; never return full saved secrets or ciphertext for browser decryption. Do not persist secrets in browser storage. Enforce [design.md](design.md)'s keep/replace/remove behavior server-side; presentation is not access control.
- Generate display-only API-key preview metadata server-side during saving; bind it to the confirmed credential and replace/clear it with that credential. Never decrypt existing secrets merely to populate settings. Allow fragments only for documented key formats with sufficient unpredictable content remaining hidden and provider rules permitting disclosure; short, unknown, or unsuitable keys return no preview. Never expose overlapping fragments, full keys, or original lengths. Passwords never have partial previews.
- Full stored-secret reveal needs an explicit product requirement, recoverable credentials, server-side user/tenant checks, recent authentication where warranted, no response caching, audit events without secret values, and prompt clearing. It must never happen while merely loading settings.
- Verify with synthetic credentials: password verification or encryption round-trip/tamper rejection, authorization, state changes, preview fallback/synchronization and denied cross-user/tenant access, and absence of unintended leaks in responses/logs/browser storage. Existing storage migrations are deliberate tested work, not a blueprint-adoption side effect.

Use current [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) guidance. Follow [packages.md](packages.md) and [updates.md](updates.md) for dependency security; production secrets stay out of update-test and merge jobs.

## Security review

Define security/data requirements in `planning`, implement during `build`, and review at `DEVELOPMENT: security`; continue through `PRODUCTION`. Verify protections before real customer-data collection, including waitlists. Use applicable requirements from latest stable [OWASP ASVS](https://github.com/OWASP/ASVS) and current stack/provider guidance.

- **Data and promises:** Trace collection, storage, APIs/vendors, logs, backups, retention, export, and deletion against policies, docs, and marketing under [legal.md](legal.md) and [offering.md](offering.md). Review policy impacts of data-practice changes; resolve mismatches before collection/publication without silently weakening approved commitments.
- **Accounts and administration:** Test authentication, administrator MFA, sessions, recovery, least privilege, and denied role/tenant access, including admin APIs and background operations.
- **Application and infrastructure:** Review code, dependencies, credentials, API/input/upload protections, hosting/storage configuration, repository/CI/deployment access, backups, and recovery. Combine automated checks, code/configuration review, and allowed/denied tests in authorized environments.
- **Abuse prevention:** Verify rate limits, login throttling, alerts, and appropriate IP restrictions using [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). Include account-based protections; shared/changing IPs undermine blanket bans and risk legitimate-user lockouts. Test applicable recovery and proxy-derived IP handling.

Record date, candidate/configuration, reference versions, scope, coverage, evidence, justified exclusions, risks, fixes, and retests in private `docs/internal/`. A clean scan alone is insufficient. Rate findings with [OWASP risk rating](https://community.owasp.org/OWASP_Risk_Rating_Methodology), recording likelihood, impact, assumptions, and rationale. Reclassification requires evidence; never lower severity merely to pass.

Unverified required controls or unresolved critical/high findings block beta/release. Only the owner may accept a specific finding in writing: privately record its severity, release/environment scope, rationale, compensating controls, remediation tracking, review/expiry date, and approval reference. Acceptance waives only that finding while valid; preserve its severity and unresolved status. Reassess at the recorded date or when scope/conditions change. Agents cannot accept risks. Acceptance cannot turn missing checks into passes, weaken customer commitments, or authorize deployment.

During `RELEASE: validation`, recheck beta fixes and final offering/data claims. Repeat affected checks for later changes.
